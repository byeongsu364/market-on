# MarketOn 온톨로지·RAG 적재 파이프라인 기획서 v1

Nov 26, 2026 · @김진용

## 요약

**한 줄 정의:** 공공데이터·손님 사진·상인 확인을 하나의 적재 파이프라인으로 받아, 짧은 사실은 온톨로지에, 긴 설명은 RAG 청크에 넣고, 둘을 `item_id`·`node_type`·`source_id` 세 키로 묶는다.

**핵심 결정 5가지**

1. **저장소는 하나:** PostgreSQL 16 한 곳에 온톨로지 테이블(노드·관계)과 pgvector 청크를 함께 둔다. 그래프 DB를 따로 두지 않아 동기화 문제가 없다.
2. **입력 경로는 셋:** ① 공공 문서·API(배치) ② 손님 사진 제보(실시간, 3명 확인) ③ 상인 확인·마감세일(실시간). 셋 다 같은 `검수 상태` 필드를 거친다.
3. **적재 순서 고정:** 수집 → 정규화(온톨로지 ID 부여) → 청크 → 검수 → 임베딩(bge-m3) → 적재 → 캐시 무효화. 온톨로지 ID가 없는 문서는 적재하지 않는다.
4. **검색은 온톨로지가 먼저:** 질문을 `item_id + intent`로 바꾼 뒤 메타데이터로 범위를 좁히고 벡터 검색한다. 숫자는 AI가 아니라 코드와 값 대조가 정한다.
5. **확장 목표:** 현재 5품목·문서 20개·출처 13곳 → 최종발표 30품목·문서 약 180개·청크 약 1,200개.

**루브릭 예상:** 현재 설계 기준 **84점 → 보완 후 90점 → 레시피 RAG 포함 92점** (8장).

## 배경과 목표

중간발표의 약속 "살까 말까, 이유를 켜 드릴게요"를 지키려면 모든 답에 출처가 붙어야 하고, 그 출처가 계속 쌓여야 한다. 이 파이프라인은 그 "쌓이는 방법"을 정한다.

중간발표에서 이어받는 전제:

- 상인도 관리자도 가격을 입력하지 않는다. 손님 사진 한 장이 쌓여 시세표가 된다(확장 기능).
- 모든 근거는 시장 안 점포로 이어진다(경동시장 108곳, 사과 판매 54곳).
- AI는 근거 문서 안에서만 말하고, 가격·수량 숫자는 코드가 정한다.

| 지표 | 현재 (11-26) | 최종발표 목표 | 연결 원칙 |
| --- | --- | --- | --- |
| 품목 수 | 5 | 30 | KAMIS 조사 품목과 일치 |
| 확인 포인트 | 20 | 120 (품목당 4) | 근거 있는 판단 |
| 근거 문서 / 출처 | 20 / 13 | 약 180 / 15 이상 | 출처 100% |
| 청크 | (미집계) | 약 1,200 | 한 청크 = 한 품목 한 주제 |
| 검수 완료 비율 | 검수 중 | P0 문서 100% | 검수 전은 "검수 전" 표시 |
| 근거 적중률 (시연 질문) | 미측정 | 30문항 중 27 이상 | 30초 안에 결정 |

목표 숫자는 제안값이에요. 팀이 확정하면 발표 슬라이드의 "30초·100%·0"과 함께 씁니다.

## 전체 아키텍처

배치(공공 문서)와 실시간(손님·상인) 입력은 검증 방식만 다르고, 모두 같은 정규화 단계를 거쳐 하나의 PostgreSQL에 들어간다. 파란 상자는 온톨로지 구성, 주황 상자는 RAG 적재다.

## 온톨로지 설계

품목(Item)을 중심에 두고, 중간발표 이후 새로 생긴 두 고리(함께 만드는 시세표·입점 요청)를 위해 **제보(Report)·입점요청(MarketRequest)·검수 상태** 세 가지를 v2 스키마에 더한다.

&#91;embedded content: 온톨로지 그래프 · 클래스 13개, 핵심 관계\]

파란 노드는 온톨로지 테이블에만 들어가는 짧은 사실, 주황 노드는 온톨로지 노드이면서 RAG 청크(고르는 법·보관법·점포 이야기·레시피)도 함께 적재되는 노드다. 왼쪽은 팀이 만드는 품목 지식, 오른쪽은 손님·상인·aT가 채우는 시장 데이터이고, 점선은 모든 노드가 근거를 가리키는 `supportedBy`다.

### 클래스 (v3)

| 영역 | 클래스 | 핵심 속성 | 채우는 경로 | 단계 |
| --- | --- | --- | --- | --- |
| 품목 지식 | `Item` | 표준명·동의어·인식 라벨·aT 코드·다국어 | 팀 구축 (`items.yaml`) | P0 |
| 품목 지식 | `Variety` | 품종명·aT 품종 코드·기본 비교 여부 | 팀 구축 + aT | P0 |
| 품목 지식 | `Criterion` | 부위·좋은 상태·피할 상태·`source_id` | 팀 작성 + 공공 문서 | P0 |
| 품목 지식 | `SaleUnit` | 단위·kg 환산 계수 | 팀 구축 | P0 |
| 품목 지식 | `Storage` · `Prep` · `Season` | 온도·기간 / 손질 / 달 | 공공 문서 | P1 |
| 시세 | `PriceObservation` | 품목·단위·날짜·지역·유통 구분·`origin`(aT/제보) | aT API (매일) | P0 |

| 시장 | `Market` → `Zone` → `Store` | 좌표·업종(8종)·취급 품목 | 소상공인 상가정보 | P0 |
| 시장 | `Sale` (마감세일) | 품목·가격·`valid_until` | 상인 30초 입력 | P0 |
| 시장 | `MarketRequest` (신규) | 요청 시장·요청 수·승인 상태 | 손님 요청 | 예정 |
| 근거 | `Source` | 기관·발행일·라이선스·`review_status` | 수집 단계 자동 | P0 |

### 핵심 관계

| 관계 | 주어 → 목적어 | 쓰임 |
| --- | --- | --- |
| `isA` · `hasGrade` | 품목 → 분류 · 품종 | 사진 인식 결과 정규화, 품종별 시세 |
| `hasCriterion` | 품목 → 확인 포인트 | 현명한 장보기 체크 |
| `hasPrice` · `soldBy` | 품목 → 시세 · 판매 단위 | 시세 대비 판정 (코드 계산) |
| `sells` · `contains` | 점포 → 품목 / 시장 → 점포 | 파는 점포·시장 지도 |
| `reportedAt` · `confirmedBy` | 제보 → 점포 / 제보 → 상인 | 함께 만드는 시세표 |
| `requests` | 입점요청 → 시장 | 수요 숫자 공개 |
| `supportedBy` | 모든 지식 노드 → 근거 | 출처 표시·환각 억제 |

### 예시 트리플 (사과)

```text
item:apple        isA            cat:fruit
item:apple        hasGrade       var:fuji          (기본 비교)
item:apple        hasCriterion   c:apple-stem      supportedBy src:nongsaro
item:apple        soldBy         unit:each         (factor 0.3kg)
store:kd-A12      sells          item:apple
report:r-0412     reportedAt     store:kd-A12      price 3,000/개  confirms 3
report:r-0412     confirmedBy    merchant:kd-A12
```

**저장 방식:** 노드는 `onto_node(id, type, props jsonb)`, 관계는 `onto_edge(subj, pred, obj, source_id)` 두 테이블로 PostgreSQL에 둔다. 원본은 `data/ontology/*.yaml`이고, 적재 스크립트가 yaml에서 테이블을 다시 만든다(Git으로 변경 이력 관리).

## RAG 적재 파이프라인 단계별 상세

적재는 7단계이고, 각 단계는 다음 단계가 읽는 파일 하나를 남겨 중간에 멈춰도 다시 시작할 수 있다.

| # | 단계 | 하는 일 | 산출물 | 실패 시 |
| --- | --- | --- | --- | --- |
| 1 | 수집 | 출처별 수집기 (농사로 API, aT 소매가격, 상가정보, 표준규격 PDF) | `raw/{source_id}/*.json` + 라이선스 기록 | 라이선스 미확인 → 수집 안 함 |
| 2 | 정제 | HTML·광고 제거, 표를 행 단위 문장으로, 단위 표기 통일 (℃, kg, 원) | `clean/*.md` | 원본 보존, 플래그 |
| 3 | 정규화 | 동의어 사전으로 `item_id` 부여, 주제로 `node_type`·`intent` 부여 | 메타데이터 붙은 문서 | `item_id` 없으면 **적재 제외** |
| 4 | 청킹 | 300\~500토큰, 격침 50, 한 청크 = 한 품목 한 주제 | `chunks.jsonl` | 너무 길면 소제목 기준 재분할 |
| 5 | 검수 | 사람이 `RAG_REVIEW.md`에서 체크, 숫자·단위 자동 추출해 대조표 생성 | `review_status` = 검수 전/완료/반려 | 검수 전도 적재하되 답에 "검수 전" 표시 |
| 6 | 임베딩·적재 | bge-m3 (1024차원) → pgvector, `chunk_hash`로 바뀐 청크만 다시 임베딩 | `rag_chunk` 테이블 | 이전 버전 유지 |
| 7 | 캐시 무효화 | 바뀐 `item_id`의 답 캐시 삭제, 회귀 테스트 실행 | 적재 리포트 | 테스트 실패 시 롤백 |

### 입력 경로 3개

| 경로 | 주기 | 온톨로지로 가는 것 | RAG로 가는 것 | 신뢰 규칙 |
| --- | --- | --- | --- | --- |
| ① 공공 문서·API | aT 매일, 문서 주 1회 | `PriceObservation`, `Criterion`, `Store` | 고르는 법·보관·제철 설명 | 검수 후 공개 |
| ② 손님 사진 제보 | 실시간 | `Report` → 확인 3명 이상이면 `PriceObservation(origin=제보)` | 없음 (숫자만) | 3명 확인 + 값 범위 검사 |
| ③ 상인 입력 | 실시간 | `Sale`, `confirmedBy`, `sells` | 점포 한 줄 소개 (동의 받은 것만) | `valid_until` 지나면 자동 숨김 |

### 청크 메타데이터 (v1에서 추가되는 필드)

- `review_status`: 검수 전 / 완료 / 반려 — 답 화면의 "검수 전" 표시와 연결
- `variety_id`: 품종별 답 (예: 후지 vs 홍로)
- `chunk_hash`: 바뀐 청크만 다시 임베딩, 캐시 무효화 키
- `numbers[]`: 청크 안 숫자·단위 목록 ("0\~2℃", "한 달") — 값 대조에 사용

기존 필드(`item_id`·`node_type`·`intent`·`source_id`·`license`·`quote_only` 등)는 \[RAG 지식베이스 v1\] 그대로 쓴다.

## 검색·생성 전략

온톨로지가 "무엇을 찾을지", RAG가 "무엇이라고 답할지", 코드가 "숫자가 맞는지"를 맡는다.

1. **정규화:** 사진 → Gemma(gemma4:e4b) 인식 → `vision_labels` 매핑 → `item_id`. 질문은 동의어 사전으로 `item_id + intent`.
2. **구조 조회 (SQL):** 시세·단위·파는 점포는 온톨로지 테이블에서 바로 가져오고 코드가 계산한다. LLM을 부르지 않는다.
3. **필터 + 벡터 검색:** `WHERE item_id = ? AND node_type IN (...)` 후 pgvector 코사인 상위 5개. 품종을 고른 경우 `variety_id`도 걸러 우선.
4. **생성:** Gemma 먼저, 답이 비거나 근거를 못 쓰면 GPT(gpt-5.4-mini)로 전환. 프롬프트는 "주어진 청크 안에서만, 없으면 '확인된 자료가 없어요'".
5. **값 대조:** 답 문장의 숫자·단위·다른 품목명을 청크의 `numbers[]`와 비교해 틀린 문장을 지운다. `quote_only` 청크는 원문 인용.
6. **출처 표시·캐시:** 실제로 쓴 청크의 출처·발행일·검수 상태를 붙이고, `item_id + intent + 날짜`로 캐시.

**한계(솔직하게 발표):** 값 대조는 숫자·단위는 잡지만 문장 의미 전체는 검증하지 못한다. 이 한계는 검수 상태 표시로 보완한다.

## 레시피 RAG

레시피는 공공 레시피 DB를 같은 파이프라인으로 적재하고, **계절·날씨·유형 세 축을 모두 담되 사람이 손으로 태그를 달지 않는다.** 유형은 원본 데이터에 있고, 계절은 재료의 제철에서 계산하고, 날씨는 규칙표로 정한다. 레시피의 역할은 "요리 알려주기"가 아니라 **재료를 같은 시장 안 점포로 이어 주는 장보기 목록**이다.

### 세 축을 다루는 방법

| 축 | 값 | 정하는 방법 | 사람 작업 |
| --- | --- | --- | --- |
| 유형 | 요리종류(밥·국&찌개·반찬·일품·후식) + 조리방법(끓이기·굽기·볶기·찌기·튀기기) + 구매 맥락(가정용·제수용·김장) | 원본 필드 그대로, 맥락은 `Context` 연결 | 없음 |

날씨 API가 실패하면 날씨 축만 빼고 계절·유형으로 추천을 이어간다(온톨로지 v2의 대체 규칙).

### 온톨로지 추가

- `Recipe`: 메뉴명·요리종류·조리방법·인분·열량·`source_id`
- `usedIn` (품목 → 레시피): 역할(주재료/부재료)·양·단위. 재료 문자열은 동의어 사전으로 `item_id`에 매핑하고, 못 찾으면 "시장 밖 재료"로 남긴다.
- `suitsWeather` (레시피 → 날씨): 규칙표로 자동 생성
- 핵심 경로: `Recipe ←usedIn— Item ←sells— Store` → "이 요리 재료 5개 중 4개를 경동시장 점포 3곳에서 살 수 있어요"

### 청킹과 메타데이터

레시피 1개 = 청크 2개(개요·재료 1 + 만드는 법 1). 한 품목 한 주제 규칙의 예외로, 레시피는 여러 품목에 걸치므로 `item_ids[]` 배열을 쓴다.

```json
{
  "chunk_id": "chk:cookrcp-0231-steps",
  "node_type": "Recipe",
  "intent": "recipe",
  "recipe_id": "recipe:cookrcp-0231",
  "item_ids": ["item:radish", "item:green_onion"],
  "main_item_id": "item:radish",
  "dish_type": "국&찌개",
  "cook_method": "끓이기",
  "season_months": [11, 12, 1],
  "weather_tags": ["cold", "snow"],
  "servings": 2,
  "kcal": 180,
  "source_id": "src:cookrcp01",
  "license": "확인 필요",
  "quote_only": true
}
```

(레시피 번호·열량은 형식 예시입니다.)

### 검색·생성

1. 촉발: 사진으로 확정한 품목, 또는 "무로 뭐 해 먹지?"
2. 구조 필터: `main_item_id` 일치 → 이번 달이 `season_months`에 있는 것 우선 → 오늘 날씨 가중치 → 선택한 유형
3. 벡터 검색: 자유 요청("아이랑 먹을 간단한 것")만 벡터로 재정렬, 상위 3개
4. 점포 연결: 재료별 파는 점포를 지도에 표시, 재료별 기준시세로 예상 장보기 비용은 **코드가 계산**
5. 생성: AI는 레시피를 새로 지어내지 않는다. 추천 이유 한 줄("추운 날, 제철 무로 끓이는 국")만 쓰고, 만드는 법은 원문과 출처를 보여 준다. 라이선스가 변경을 허용하면 3단계 요약을 추가한다.

### 분량과 일정

- 목표: 30품목 × 주재료 레시피 5개 = **레시피 약 150개, 청크 약 300개** (레시피 DB에서 주재료가 시연 품목인 것만 고름)
- 일정: 중간발표의 "레시피(3단계) 예정"을 3차에 배치. 파이프라인은 그대로 쓰고 수집기와 재료 매핑만 추가한다.
- 품질 검사 추가: 주재료 매핑률(목표 95%), 계절 계산이 빈 레시피 수, 시연 질문에 레시피 문항 5개 추가

### 단점을 장점으로 (레시피)

| 단점 | 장점으로 바꾸는 표현 | 적용 가능성 |
| --- | --- | --- |
| 레시피 앱은 이미 많음 | "레시피가 목적이 아니라 **재료를 우리 시장 점포 여러 곳으로 이어 주는 장보기 목록**이에요. 한 점포가 아니라 시장 전체를 홍보해요" | **9/10** |
| AI가 레시피를 만들지 않음 | "식약처 레시피 원문을 보여 줘서 **틀린 분량·위험한 조리법이 나올 수 없어요**" | **9/10** |
| 날씨 추천이 규칙이라 단순해 보임 | "날씨가 왜 이 요리를 골랐는지 **한 줄로 설명할 수 있는 추천**이에요" | **7/10** |
| 재료 일부는 시장에 없음 | "없는 재료는 '시장 밖 재료'로 솜직하게 표시하고, 이 수요가 **입점 요청 숫자**로 쌓여요" | **8/10** |

**루브릭 영향:** 창의성 +1(재료 → 점포 경로), 활용성 +1(시장 전체 홍보). 구현 시 예상 총점 90 → **92점**.

## 품질·평가·운영

적재할 때마다 자동 검사 4개와 시연 질문 30개 회귀 테스트를 돌려, 지금의 자동 테스트 545개에 RAG 품질 테스트를 더한다.

| 검사 | 기준 | 막는 문제 |
| --- | --- | --- |
| 온톨로지 연결 | 모든 청크에 `item_id`·`node_type` 있음, yaml에 있는 ID인지 | 다른 품목 문서 섞임 |
| 출처·라이선스 | `source_id`·`license` 비어 있으면 실패 | 출처 없는 답, 저작권 |
| 중복 | `chunk_hash` 같은 청크 1개만 | 같은 근거 반복 |
| 제보 가격 범위 | aT 시세의 0.3\~3배 밖이면 보류 | 오타·장난 제보 |

**평가 지표 (시연 질문 30개, 5품목 × 의도 6종 중 고름)**

- 검색 적중률: 정답 청크가 상위 5개에 드는 비율 — 목표 90%
- 출처 표시율: 답마다 출처 — 목표 100%
- 값 대조 통과율: 숫자가 근거와 일치 — 목표 100%
- "자료 없음" 정답률: 일부러 넣은 범위 밖 질문 5개에 모두 모른다고 답하는지
- 응답 시간: 캐시 적중 1초 안, 새 질문 5초 안 (30초 결정 목표의 일부)

**갱신 주기:** aT 소매가격 매일 1회, 공공 문서 주 1회 변경 확인, 상가정보 분기 1회, 제보·상인 입력은 실시간.

**개인정보:** 손님은 가입 없이 익명, 사진은 가격·품목만 추출 후 원본을 지정 기간 뒤 삭제(보관 기간은 팀 확정 필요). 사진에 사람 얼굴이나 간판 외 개인 정보가 있으면 반려. 상인 소개 문구는 동의 문구를 보여준 뒤에만 RAG에 넣는다.
