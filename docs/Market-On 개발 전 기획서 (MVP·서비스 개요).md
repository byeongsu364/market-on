# Market-On 개발 전 기획서 (MVP·서비스 개요)

Nov 22, 2026 · @김진용

## 요약 · 문서화 순서

**결론: "왜·누구에게 → 무엇을 → 어떻게 → 언제·누가 → 무엇이 틀어질 수 있나 → 어떻게 보여 줄까" 순서로 10개 문서를 쓴다.** 앞 문서가 뒤 문서의 입력이 되도록 배치했고, 대회 전에는 설계까지만 하고 코드·데이터셋은 현장에서 만든다(서약서 1항).

- 개발 착수 전 반드시 확정할 것 3가지: **① 제출된 신청서의 기능 목록(결과물과 일치해야 함) ② P0 범위 ③ 시연 시장 1곳**
- 기존 자료(온톨로지 v2, RAG v1, 설계 발표, 프론트 초안)는 ③·⑤·⑥에 그대로 흡수하고, 이 문서는 그 위의 **단일 기준서(Single Source of Truth)** 역할을 한다.

| 순서 | 문서 | 답하는 질문 | 입력(앞 문서) | 기존 자료 활용 | 완료 기준 |
| --- | --- | --- | --- | --- | --- |
| ① | 서비스 개요 | 왜, 무엇을 푸나 | 대회 주제·신청서 | 컨텍스트 v1 3·6장 | 한 줄 정의·문제·차별점 팀 합의 |
| ② | 사용자·시나리오 | 누가, 언제 쓰나 | ① | 온톨로지 v2 4장 | 페르소나 3명, 핵심 시나리오 1개 |
| ③ | 기능 정의·MVP 범위 | 무엇을 만들고 무엇을 뺄까 | ①② | 서식2 기능 목록 | P0/P1/P2 + 제외 목록 + 수용 기준 |
| ④ | 화면 설계 | 어떻게 보이나 | ③ | 프론트 초안 5화면 | 화면 목록·흐름 확정 |
| ⑤ | 데이터·지식 설계 | 무엇을 근거로 답하나 | ③ | 온톨로지 v2, RAG v1 | P0 노드·문서·출처 목록 |
| ⑥ | 아키텍처·기술 스택 | 어떻게 동작하나 | ③⑤ | 설계 발표 4층 구조 | 구성도 + 스택 표 |
| ⑦ | API 명세 | 프론트·백엔드가 무엇을 주고받나 | ④⑥ | 온톨로지 v2 4-6 JSON | 엔드포인트 표 + 예시 |
| ⑧ | 일정·역할 | 언제, 누가 | ③⑦ | 단점 전략 #11 | 시간대별 담당표 |
| ⑨ | 리스크·대응 | 무엇이 틀어질 수 있나 | ③\~⑧ | 단점→장점 전략 | 리스크별 대체 경로 |
| ⑩ | 시연·성공 지표 | 무엇을 보여 주고 어떻게 판단하나 | 전체 | 설계 발표 7장 | 시연 대본 + 체크리스트 |

① → ③이 가장 중요하다. 범위가 흔들리면 뒤 문서를 모두 다시 써야 한다.

## ① 서비스 개요

**Market-On은 전통시장 상품 앞에서 "이걸 살까"를 소비자가 스스로 판단하도록 근거를 주고, 그 판단을 시장 안 점포 방문으로 잇는 모바일 웹 서비스다.** 한 줄 버전은 "시장 안에서, 이 상품을, 내가 판단한다."

### 문제 정의

1. **정보 부족:** 전통시장 농축수산물은 품질·가격을 비교할 정보가 없어 소비자가 구매를 망설인다.
2. **디지털 공백:** 서울시 분석 기준 시장 안 점포의 디지털 지도 등록률은 12% 미만이다. 상인은 홍보 수단이 거의 없다.
3. **가격만 좇으면 손해:** Wayket 실험에서 최저가 시장만 고르면 평균 39km를 이동해 총비용이 2배가 됐다. "가까운 시장에서 현명하게 사기"가 답이다.

### 해결 방식 (사용자 흐름)

1. **찍고** — 사진 1장으로 품목 인식, 사용자가 확정
2. **판단하고** — 품목별 확인 포인트(근거 포함) + KAMIS 기준시세 대비 가격 위치
3. **찾고** — 같은 품목을 파는 시장 안 점포를 카테고리 미니맵에서 강조
4. **함께 산다** — 함께 사기·상인 오늘 추천으로 여러 점포 방문 유도

### 가치 제안

| 대상 | 얻는 것 | 지표(시연에서 보여 줄 것) |
| --- | --- | --- |
| 소비자 | 출처가 붙은 판단 근거, 기준시세 대비 가격 | 사진 → 결과까지 시간, 답변마다 출처 표시 |
| 상인(소상공인) | 인식 품목 → 내 점포 연결, 오늘 추천 홍보 | 점포 노출 횟수, 오늘 추천 등록 30초 |
| 외국인 방문객 | 다국어 품목명·확인 포인트 | 5개 언어 라벨 |

### 차별점 4가지

| 축 | 기존 서비스 | Market-On |
| --- | --- | --- |
| 쓰는 장소 | 집에서 "어디서 살까" (알뜰하게 장볼지도, 배달앱) | 시장 현장에서 "이걸 살까" |
| 판단 주체 | AI가 신선도 등급 판정 (신선도 앱) | 소비자가 확인 포인트로 판단 |
| 근거 출처 | 생성형 AI의 말 | 온톨로지 + RAG, 답변마다 출처 |
| 혜택 대상 | 소비자 | 소비자 + 상인(점포 연결·오늘 추천) |

> 발표 문구: 기존 서비스가 "시장에 어떻게 가나", "집에서 어떻게 사나", "어디가 싼가"를 해결했다면, Market-On은 시장 안에서 상품 앞에 선 순간의 판단을 돕는다.

**열린 질문:** 실제 제출한 신청서가 v4("AI 신선도 판별", 대시보드 포함)인지 최신안("소비자 판단", 점포 지도)인지 확인해야 한다. 신청서는 수정할 수 없으므로 결과물과 다른 부분은 ⑨에서 발표 멘트로 연결한다.

## ② 타깃 사용자 · 핵심 시나리오

**주 사용자는 "시장에 익숙하지 않은 2030 소비자"이고, 상인과 외국인은 보조 사용자다.** 개인정보(이름·연락처·나이·성별)는 받지 않으므로 페르소나는 행동과 상황으로 구분한다.

| 페르소나 | 상황 | 망설이는 이유 | Market-On이 주는 것 | 우선순위 |
| --- | --- | --- | --- | --- |
| A. 자취 초보 (20대 대학생·사회초년생) | 퇴근길 동네 시장, 1\~2인분 장보기 | 싱싱한지 모름, 가격이 적당한지 모름, 물어보기 민망 | 확인 포인트 3개, 기준시세 대비 ±%, 함께 사기 점포 | P0 |
| B. 시장 상인 (50대 청과 점포) | 손님이 지나치기만 함, 홍보 수단 없음 | 앱이 어렵고 입력할 시간이 없음 | 최초 1회 점포·취급 품목 등록, 오늘 추천 30초 | P1 |
| C. 외국인 방문객 | 시장 구경·먹거리 탐방 | 품목명을 모름, 한국어 안내문 | 다국어 라벨(ko·en·zh·ja·vi) | P1 |

### 핵심 시나리오 (페르소나 A, 대파 한 단)

1. 시장 입구에서 앱을 열면 GPS로 시연 시장이 자동 선택된다. (필수 입력 ① 시장)
2. 채소 가게 앞에서 대파를 찍는다. Vision 라벨 "green onion"이 `item:green_onion`으로 매핑되고, 신뢰도가 낮으면 후보 3개에서 고른다. (필수 입력 ② 사진)
3. 결과 화면에 확인 포인트 3개가 나오고, 각 항목에 출처(예: 농사로)가 붙는다. 사용자가 직접 체크한다.
4. 가격표의 3,500원을 입력하면 "기준시세(1단 환산 3,980원) 대비 12% 저렴"이 나온다. 조사지역·조사일을 함께 표시한다.
5. "이 시장에서 대파를 파는 점포" 버튼으로 미니맵이 열리고, 채소 구역 점포 3곳이 강조된다.
6. (P1) "함께 사기: 두부·양파"와 상인 오늘 추천이 나오고, 반찬·청과 점포로 동선이 이어진다.

보조 시나리오: 상인 B가 점포를 탭하고 취급 품목을 고른 뒤, 오늘 추천(단감 5개 1만 원)을 올리면 소비자 지도에 바로 뜨는 흐름 1개만 시연한다.

## ③ 기능 정의 · MVP 범위

**MVP(P0)는 "찍고 → 판단하고 → 찾는" 5개 기능이고, 24:00까지 끝내면 시연이 성립한다.** P1은 기술성·차별점을 올리는 기능, P2는 여유가 있을 때만 하거나 로드맵으로 발표한다. 기준은 온톨로지 v2(2026-11-22)다.

| ID | 기능 | 신청서 기능 | 수용 기준 (이것이 되면 완료) | 단계 |
| --- | --- | --- | --- | --- |
| F1 | 지식 기반 (온톨로지 + RAG) | 3 | 시연 품목 30개 노드, P0 문서(A·B·C) 적재, 질문 10개 중 8개 이상 출처 포함 답변 | P0 |
| F2 | 사진 품목 인식 + 사용자 확정 | 1 | 시연 품목 10개 사진에서 후보 3개 안에 정답, 사진 → 결과 5초 이내 | P0 |
| F3 | 품목별 확인 포인트 안내 | 1 | 품목마다 포인트 3개 + 출처, 등급·"구매 추천" 문구 없음 | P0 |
| F4 | KAMIS 기준시세 비교 | 2 | 입력 가격 vs 기준시세 ±%, 판매 단위 환산, 조사지역·조사일 표시, 결측 시 대체값 | P0 |
| F5 | 시장 내 점포 카테고리 지도 | 6 | 시연 시장 1곳 점포 20\~30곳, 인식 품목 판매 점포 강조 | P0 |
| F6 | 근거 기반 답변·환각 억제 | 3 | 근거 없으면 "확인된 자료가 없어요", 답변마다 출처 | P1 |
| F7 | AI 구매 추천 Agent (가정용·선물용·제수용, 예산) | 4 | 목적·예산 입력 → 품목 3개 + 이유 + 판매 점포 | P1 |
| F8 | 상인 오늘 추천 (점포·취급 품목 등록 포함) | 5 (상인 홍보) | 등록 → 소비자 지도·결과 화면에 즉시 표시, 유효기간 지나면 숨김 | P1 |
| F9 | 다국어 (ko·en·zh·ja·vi) | 5 | 시연 품목 10개 라벨 + UI 문구 전환 | P1 |
| F10 | 온톨로지 기반 응답 캐시 | — | "대파 값"과 "파 가격"이 같은 캐시 적중 | P1 |
| F11 | 함께 사기·장보기 동선 | 6 | 인식 품목 → pairsWith 품목 → 같은 시장 점포 순서 | P2 |
| F12 | Gemini ⇄ Gemma 모델 전환 | AI 도구 | 설정 1개로 전환, 같은 질문 두 모델 답변 비교 | P2 |
| F13 | 구매 판단 카드 (공유 이미지) | 5 | 시안·템플릿은 보관, 여유 시 F8 화면 재활용 | P2 |

### 제외 범위 (만들지 않음)

- **AI 신선도 등급 판정** — 책임 문제, 소비자 판단 원칙과 충돌
- **판매 로그 트렌드 대시보드** — 판매 데이터 출처 없음
- **레시피 추천** — 알뜰하게 장볼지도와 정면 중복, F11의 연결 고리로만 사용
- **온누리상품권 사용처** — 정부가 네이버·카카오 지도로 제공 예정
- **회원가입·결제·주문** — 현장 판단이 목적

### 시연 최소 조건

F1\~F5만 완성돼도 ⑩의 핵심 시연(대파 한 단)은 끝까지 간다. P1 중 하나만 고른다면 **F8 상인 오늘 추천**을 먼저 한다. 대회 주제(소상공인 홍보)에 가장 직접 닿는다.

## ④ 화면 설계

**소비자 6화면 + 상인 2화면, 하단 탭 4개(홈·찍기·지도·추천)로 구성한다.** 프론트 초안 5화면에서 ⑤ 트렌드 대시보드를 빼고 점포 지도·인식 확정·상인 화면을 더했다. 색은 진녹 #16301F, 주황 #E8743B, 크림 #F7F5EE, 폰트 Noto Sans KR(로고 시안 확정 후 재검토).

| ID | 화면 | 보여 주는 것 | 기능 | 초안 대비 | 단계 |
| --- | --- | --- | --- | --- | --- |
| S1 | 홈 | 현재 시장, 찍기 버튼(가장 크게), 오늘 기준시세 3품목, 상인 오늘 추천 | F4·F8 | 제철 카드 → 오늘 추천으로 교체 | P0 |
| S2 | 촬영·인식 확정 | 카메라/앨범, 후보 3개(신뢰도 낮을 때), 검색 | F2 | 신규 | P0 |
| S3 | 구매 판단 결과 | 확인 포인트 체크리스트+출처, 가격 입력 → 기준시세 ±%, "파는 점포 보기" | F3·F4·F6 | 등급 문구 삭제, 레시피 탭 → 함께 사기 | P0 |
| S4 | 시장 점포 지도 | 시장 평면도형 미니맵, 구역 색(청과·채소·수산·정육·반찬·떡/분식), 품목 판매 점포 강조 | F5 | 신규 | P0 |
| S5 | 점포 상세 (바텀시트) | 점포명, 취급 품목, 영업시간, 오늘 추천 | F5·F8 | 신규 | P0 |
| S6 | AI 구매 추천 | 목적·받는 사람·예산 칩 → 추천 3개 + 근거 + 점포, (P2) 모델 전환 | F7·F12 | 기존 ④ 유지 | P1 |
| M1 | 상인 점포 등록 | 지도에서 내 점포 탭, 취급 품목 칩 | F8 | 신규 | P1 |
| M2 | 오늘 추천 올리기 | 품목 탭, 가격, 한 줄 소개, 유효기간, 홍보 동의 문구 | F8 | 기존 ⑤ 대체 | P1 |

### 화면 흐름

1. S1 홈 → 찍기 → S2 인식 확정 → S3 결과
2. S3 → "파는 점포 보기" → S4 지도(해당 점포 강조) → S5 점포 상세
3. S1 → 추천 탭 → S6 → 추천 품목 탭 → S4
4. 상인: M1 (최초 1회) → M2 → S1·S5에 즉시 반영

### 화면 원칙

- 필수 입력은 사진 1장과 시장 선택 1번. 나머지는 탭·칩, 자유 입력은 가격과 질문뿐
- 결과 화면에 "신선·추천" 같은 판정 문구를 쓰지 않는다
- 모든 숫자·지식 아래에 출처·날짜를 작게 표시한다
- 시장에서 한 손으로 쓰도록 주요 버튼은 화면 하단에 둔다

할 일: 프론트 초안 아티팩트 소유자가 S2·S4·S5·M1·M2 와이어프레임을 추가하고 S3 문구를 고친다. (코드가 아닌 화면 초안이므로 사전 준비 허용)

## ⑤ 데이터 · 지식 설계

**온톨로지는 "무엇을 찾을지", RAG는 "무엇이라고 답할지"를 맡는다.** 상세 스키마는 `온톨로지_아키텍처_v2`, 문서 규칙은 `RAG_지식베이스_v1`을 따르고, 여기에는 개발 착수에 필요한 P0 범위만 고정한다.

## ⑥ 시스템 아키텍처 · 기술 스택

**서비스 → AI Agent → Knowledge Layer → 데이터 4층 구조이고, 모든 질문은 반드시 온톨로지 정규화를 거친 뒤 LLM에 닿는다.** 역할 분담은 "Vision은 인식, 온톨로지는 정규화, RAG는 근거, Gemini는 문장, KAMIS는 가격"이다. Vision과 Gemini를 둘 다 쓰는 이유가 이 분담이다.

### 요청 처리 순서 (사진 1장)

1. 프론트가 사진을 백엔드로 보낸다 (키는 백엔드에만)
2. Vision 라벨 → 온톨로지 `vision_labels` 매핑 → 후보 3개
3. 사용자가 확정한 `item_id`로 확인 포인트·점포를 그래프에서 조회 (LLM 호출 없음)
4. KAMIS 시세 조회 → 단위 환산 → ±% 계산
5. 질문·추천만 LLM 경로: 캐시 확인 → 메타데이터 필터 → 벡터 검색 → Gemini 생성 → 근거 검증 → 출처 부착 → 캐시 저장

P0 핵심 흐름(1\~4)은 LLM 없이도 동작한다. Gemini가 느리거나 막혀도 시연이 멈추지 않는다.

### 기술 스택 (제안 — 팀 확정 필요)

| 층 | 선택 | 이유 |
| --- | --- | --- |
| 프론트 | React + Vite, PWA, Tailwind | 바이브코딩 도구가 가장 잘 다루는 조합, 모바일 웹 바로 배포 |
| 미니맵 | SVG 직접 그리기 (시장 평면도형) | 시장 내부는 지도 API에 없음, 좌표는 Store에 저장 |
| 백엔드 | Python FastAPI | rdflib·벡터DB·Gemini SDK가 모두 Python |
| 온톨로지 | JSON-LD 파일 + rdflib | 별도 그래프DB 없이 메모리 조회, 배포 단순 |
| RAG | Chroma + 임베딩 모델 \[확인 필요\] | 로컬 파일 기반, 메타데이터 필터 지원 |
| LLM | Gemini API (`llm_client` 한 곳에서 호출) | 설정 하나로 Gemma 전환(F12) |
| 캐시 | 딕셔너리 또는 SQLite, 키 = item\_id + intent + 날짜 | 외부 서비스 없이 구현 |
| 배포 | \[확인 필요\] 프론트 정적 호스팅 + 백엔드 1대 | 심사위원이 QR로 직접 접속하게 |
| 협업 | GitHub 저장소(대회 당일 생성), Claude Code·Cursor | 커밋 이력 = 현장 개발 증거 |

### 원칙

- API 키(KAMIS·Vision·Gemini·카카오)는 백엔드 `.env`에만, 저장소에 올리지 않는다
- 저장소는 대회 당일 14:30 이후 만든다. 첫 커밋 시각이 사전 제작물 없음을 보여 준다

## ⑦ API · 인터페이스 명세

**P0는 엔드포인트 6개이고, 모든 요청·응답은 온톨로지 노드 ID(`item:`, `market:`, `store:`)로 주고받는다.** 프론트·백엔드가 이 표를 먼저 합의하면 1차 개발을 동시에 시작할 수 있다. 프론트는 처음에 아래 예시 JSON을 목(mock)으로 쓴다.

| 메서드 · 경로 | 입력 | 출력 | 화면 | 단계 |
| --- | --- | --- | --- | --- |
| `GET /markets/nearby` | lat, lng | 시장 목록(가까운 순) | S1 | P0 |
| `POST /recognize` | 사진(multipart) | vision\_labels, 후보 3개(item\_id, 이름, 신뢰도) | S2 | P0 |
| `GET /items/{item_id}` | lang | 확인 포인트(+source), 기본 판매 단위, 다국어 라벨 | S3 | P0 |
| `GET /price` | item\_id, market\_id, unit, seen\_price? | 기준시세(단위 환산), ±%, 조사지역·조사일, fallback 여부 | S1·S3 | P0 |
| `GET /markets/{market_id}/map` | item\_id? | 구역·점포 좌표, item\_id를 파는 점포 highlight | S4·S5 | P0 |
| `GET /health` | — | 외부 API 상태(시연 전 점검용) | — | P0 |
| `POST /ask` | question, item\_id?, lang | answer, sources\[\], cache\_hit | S3 | P1 |
| `POST /recommend` | purpose, relation?, event?, budget, headcount | 품목 3개 + 이유 + 점포 + sources | S6 | P1 |
| `POST /stores/{store_id}/picks` | item\_id, price, note, valid\_until | TodayPick | M2 | P1 |

### 응답 예시 — `GET /price`

```json
{
  "item_id": "item:green_onion",
  "unit": "unit:bunch",
  "reference_price": 3980,
  "seen_price": 3500,
  "diff_pct": -12,
  "region": "서울",
  "observed_on": "2026-11-27",
  "fallback": null,
  "source": "src:kamis"
}
```

### 약속

- 에러는 `{"error": {"code", "message"}}` 한 형식, 외부 API 실패 시 `fallback` 필드에 사용한 대체값 종류(`region_avg` · `national_avg` · `last_valid`)를 넣는다
- 모든 지식·가격 응답에 `source`가 빠지면 테스트 실패로 본다
- 경로·필드 이름은 온톨로지 v2 4-6 JSON과 같은 이름을 쓴다
